## Build Philosophy

1. **Each phase ships something usable.** No phase leaves the app broken; every phase ends with a demoable route and verification path.
2. **Infrastructure before features.** RLS, migrations, generated types, tests, and observability precede trip data that a family might trust.
3. **Magic moment first.** The canonical CSV becomes a readable itinerary with correct sourced conflicts by the end of Phase 1.
4. **Test as you go.** Fixtures, rule evaluators, RLS policies, and core journeys gain tests in the same task that introduces behavior.
5. **Progressive enhancement.** Start with faithful import and read flows, then add optimistic editing, realtime, and offline resilience.
6. **Review before proceeding.** Complete each phase on its own branch, open a PR, and use CodeRabbit or another review agent before merging.
7. **Preserve intent.** Never “fix” imported data silently; store the source and make every correction or override explicit.
8. **Rules are evidence.** A rule without applicability dates, verification time, and source cannot create a confident product claim.

Use CodeRabbit or another automated review agent; address findings on the same branch and merge before starting the next phase. If GitHub review is intentionally skipped, still run every verification step and record that the external-review quality gate was omitted.

### Session Tips

- Do not load the entire PRD when a phase lists focused sections.
- Do not skip RLS, import atomicity, or rule-provenance work to reach visual features faster.
- Treat `data/trip-2026.json` as the acceptance fixture, not production-only seed data.
- Keep visual values in `docs/design.md`; do not duplicate token constants in feature components.
- When a requirement conflicts with current official behavior, preserve the plan, record the dated evidence, and escalate rather than guessing.

### Prompt Templates

**Starting a new phase:**

> “Read `docs/product-roadmap.md` and find the current phase. Read only its listed references from the PRD, product vision, and design system. Start at the first unchecked task, verify it, mark it `[x]`, and continue in order.”

**Resuming after a break:**

> “Read `docs/product-roadmap.md`, find the first unchecked task in the current phase, reload only that phase's references, and continue. Preserve all completed task checkboxes.”

**After completing a phase:**

> “Update roadmap status, create `phase-{N}/{slug}`, commit and push the completed phase, then open a PR titled `Phase {N}: {Title}` with the goal, task range, verification steps, and references.”

**Fixing an issue:**

> “Read the specific PRD requirement and edge-case table for this issue, implement the smallest safe fix, and run its related unit/integration/e2e tests before changing any roadmap checkbox.”
